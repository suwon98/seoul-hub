# 트러블슈팅 이력 (Troubleshooting History)

## pnpm 빌드 스크립트 차단 오류 (ERR_PNPM_BANNED_BUILD)

### 1. 현상 (Issue)
- 모노레포 패키지 환경 조립 도중 최상위 루트 터미널에서 프론트엔드(Next.js) 의존성을 설치하고 앱을 가동하려 했으나, 보안 컴파일러 및 의존성 주입이 아래 로그를 뿜으며 전면 중단됨.
```text
ERR_PNPM_BANNED_BUILD  The package Next.js wanted to run a custom postinstall script but it was blocked by active security policy.
Progress: resolved 1, reused 0, downloaded 0, added 0
```

### 2. 원인 분석 (Root Cause)
- pnpm v11 이상 버전부터 아키텍처 보안 정책이 크게 강화됨. 이에 따라 신뢰 영역으로 등록되지 않은 패키지가 임의로 외부 네이티브 바이너리 빌드 및 `postinstall` 후속 스크립트를 실행하는 행위를 기본값으로 차단함. Next.js의 SWC 컴파일러 툴체인이 이 보안 제약에 걸려 발생함.

### 3. 해결 방안 (Resolution)
- 프로젝트 최상위 루트 파워쉘 스크립트 터미널에서 다음 명령어를 실행하여 해당 모듈의 빌드 권한을 수동 승인함.
```powershell
pnpm approve-builds next
```
- 프로젝트 전역 `.npmrc` 구성 파일에 하위 패키지들의 바이너리 허용 명세를 명시적으로 기록하여 조치 완료함.

### 4. 재발 방지 및 교훈 (Prevention & Lesson)
- 모노레포 구축 시 패키지 매니저의 메이저 업그레이드 보안 변경점을 상시 모니터링해야 함. 향후 외부 엔진(Rust/C++ 바이너리 등)을 사용하는 무거운 컴파일러 라이브러리를 추가할 때는 `.npmrc` 화이트리스트 정책을 선제적으로 구성해야 함.

## GitHub Actions YAML 문법 파싱 오류 (pnpm 버전 해석 실패)

### 1. 현상 (Issue)
- 자동 배포 및 빌드를 위해 `.github/workflows/ci.yml` 스크립트를 푸시했으나, 워크플로우 가동 초입부에서 컴파일 에러를 내며 파이프라인 전체가 즉시 격추됨.
```text
🔴 Error: GitHub Actions 스크립트 파싱 실패. 
Invalid type for 인자 'version'. Expected String, but received Number (11.3).
```

### 2. 원인 분석 (Root Cause)
- GitHub Actions 가상 머신의 YAML 인프라 파서 알고리즘 특성상, `version: 11.3` 또는 `11.3.0`과 같이 소수점이 박힌 구체적 버전을 따옴표 없이 기입하면 엔진이 이를 텍스트가 아닌 실수형 수치 데이터(Number) 타입으로 강제 오인 파싱하여 내부 타입 바인딩 규격이 깨진 것임.

### 3. 해결 방안 (Resolution)
- 빌드 자동화 스크립트 내부의 pnpm 주입 버전을 명시적인 문자열 상수로 묶어 수정 조치함.
```yaml
# 기존 수치형 인자에서 문자열 싱글 쿼테이션 구조로 교정
with:
  version: '11.3.0'
```

### 4. 재발 방지 및 교훈 (Prevention & Lesson)
- 인프라를 자동 제어하는 YAML 지시어 스크립트 내에서 버전 정보나 시스템 환경 변수 수치를 기록할 때는 묵시적 형변환 오류를 차단하기 위해 무조건 따옴표(`' '` 또는 `" "`)를 붙여 데이터 무결성을 보장해야 함.

## CI 가상 환경 내 하이버네이트 DB 연결 실패 및 빌드 크래시 오류

### 1. 현상 (Issue)
- 로컬 환경에서는 빌드 및 테스트가 완벽하게 돌아갔으나, 깃허브 원격 커밋 직후 GitHub Actions 가상 러너 환경의 테스트 통합 검증 단계에서 스프링 부트 빈 초기화 도중 에러가 터지며 배포 프로세스가 차단됨.
```text
org.springframework.bean.factory.BeanCreationException: Error creating bean with name 'entityManagerFactory': 
Cannot open connection; Connection refused to jdbc:mariadb://localhost:3306/seoul_hub
```

### 2. 원인 분석 (Root Cause)
- 실제 상용 구동용 `application.yaml` 설정 파일 내부에 로컬 물리 마리아DB 연결 정보가 기본값으로 하드코딩되어 있었음. GitHub Actions 가상 리눅스 서버 내부에는 별도의 MariaDB 데몬 인프라가 존재하지 않으므로, JPA가 부팅 시 데이터 모델을 스캔하고 검증하는 연결 통로(HikariPool) 확보에 실패해 발생한 구조적 에러임.

### 3. 해결 방안 (Resolution)
- 백엔드 빌드 명세서(`build.gradle`) 환경에 가상 메모리 테스트 전용 H2 데이터베이스 의존성을 보강 주입함.
```groovy
testRuntimeOnly 'com.h2database:h2'
```
- 이후 `src/test/resources/application.yaml` 경로로 독립 테스트 구성 파일을 배치하고, 테스트 환경 가동 시에는 실제 물리 주소 대신 가상 메모리 DB를 MySQL 도플갱어 모드로 가동하도록 설정을 분리함.

### 4. 재발 방지 및 교훈 (Prevention & Lesson)
- 지속적 통합(CI) 가상 엔진은 로컬 머신의 특정 물리 인프라 자원에 절대로 종속되어서는 안 됨. 프로덕션 소스 런타임과 테스트 인프라 환경 사양을 완벽히 분리 격리하여 언제 어디서나 빌드가 가능한 무설치 격리 검증 사양을 유지해야 함.

## GitHub Actions 노션 API 환경 변수 유실 오류

### 1. 현상 (Issue)
- OpenAPI 데이터 규격을 읽어 Notion 문서 데이터베이스에 실시간 적재하는 Node.js 내부 빌드 스크립트(`sync-to-notion.js`)가 가상 머신 런타임 내에서 환경 변수를 누락하여 빌드가 드롭됨.
```text
🔴 Notion API Webhook Error: NOTION_TOKEN is undefined.
process.exit(1) with code 1. Build Failed.
```

### 2. 원인 분석 (Root Cause)
- 자동화 스크립트 명세 구조상 자바스크립트 전역 컨텍스트 내부의 `process.env.NOTION_TOKEN`과 `DATABASE_ID` 보안 자산을 조준하도록 설계해 두었으나, 깃허브 가상 컴퓨터 인프라 보안 정책상 외부 저장소의 시크릿 변수 바인딩 명세를 YAML 파일에 가리켜주지 않아 빈 값으로 증발한 누락 사고임.

### 3. 해결 방안 (Resolution)
- GitHub 저장소 웹 콘솔의 Settings -> Secrets and Variables -> Actions 스토리지 공간으로 진입하여 노션에서 공수해 온 암호화 시크릿 토큰 키 쌍을 물리적으로 바인딩함.
- 이후 CI 자동화 파이프라인 스크립트 내부 스텝 서브루틴에 환경 변수 전달 지시어를 아래와 같이 정확히 주입함.
```yaml
env:
  NOTION_TOKEN: ${{ secrets.NOTION_TOKEN }}
  NOTION_DATABASE_ID: ${{ secrets.NOTION_DATABASE_ID }}
```

### 4. 재발 방지 및 교훈 (Prevention & Lesson)
- 시스템 자동화 스크립트를 외부 API 인프라와 묶어 연동할 때는 로컬 환경의 민감한 자산(`.env`)이 외부 노출되는 것을 철저히 차단해야 함. 반드시 소유 권한이 검증된 CI 가동 인프라 플랫폼의 암호화 보관소를 경유하여 안전하게 토큰 자격 증명을 가상 머신 위로 올려주어야 함.

## MariaDB 11.x OS 인증 플러그인(GSSAPI) 충돌 및 데이터 디렉터리 부재로 인한 엔진 기동 오류

### 1. 현상 (Issue)
- 로컬 DB 인프라 가동 이후 HeidiSQL 등의 제어 도구 및 백엔드 스프링 부트에서 포트 `3306` 정문 진입을 시도했으나, 데이터베이스 자격 증명 락 및 소켓 통신 거부 에러를 내며 인프라 통로가 봉쇄됨.
```text
Access denied for user 'root'@'localhost' (using password: NO)
Can't connect to server on '127.0.0.1' (10061)
```

### 2. 원인 분석 (Root Cause)
- MariaDB v11 대 메이저 인프라 설치 패키지 구동 시 디폴트로 켜지는 `GSSAPI (Windows Authentication)` 모듈의 통합 인증 정책 시스템이 원인임. OS 관리자 계정 자격 증명과 DB의 root 마스터 권한이 하드하게 락인(Lock-in)되어, 정상적인 패스워드 주입 방식 및 외부 애플리케이션의 정방향 데이터 진입을 악성 침입으로 판단해 거부함.
- 추가로 이를 해제하기 위해 `--skip-grant-tables` 인증 스킵 옵션을 주었으나, 해당 엔진 버전은 레지스트리에 박혀있던 실제 물리 데이터 저장 공간 주소(`D:\mariadb`) 파라미터(`--datadir`)를 명시적으로 조준해주지 않으면 무결성 정책 위반으로 판단하여 즉시 스스로 프로세스를 비정상 폭파(`Aborting`)하는 폐쇄 특성을 지님.

### 3. 해결 방안 (Resolution)
- 파워쉘 터미널을 열고 윈도우 레지스트리에 잔존하던 유령 데몬 서비스 문지기를 완전히 물리적으로 격파 소멸시킴.
```powershell
sc delete MariaDB
```
- 이후 기존 데이터 디렉터리 파츠를 깨끗하게 지우고 새 설치 파일을 실행하되, 보안 장벽의 주범인 **`[ ] Enable Plugin GSSAPI (Windows Authentication)`** 항목의 체크박스를 반드시 **해제(X)** 하고 정방향 네이티브 패스워드 방식(**`1234`**)을 수동 주입하여 시스템을 청정 복구함.

### 4. 재발 방지 및 교훈 (Prevention & Lesson)
- 백엔드 애플리케이션 서버와 데이터베이스 인프라를 통합할 때, OS 계정 커널에 종속되는 특수 인증 플러그인을 기본값으로 수용하면 이식성이 극도로 저하되고 포트 경로 제어가 완전히 차단됨. 무조건 범용 정방향 TCP/IP 표준 네이티브 패스워드 인증 체계(`mysql_native_password`)를 정착시켜야 뒤탈이 없음.

## API 계약(Contract) 미스매치 및 영속성 컨텍스트 쓰기 지연에 따른 가입 중복 예외 (Race Condition)

### 1. 현상 (Issue)
- 프론트엔드 화면상에서는 이메일 중복 검증을 안전하게 마쳤으나, 가입 버튼을 눌렀을 때 성공 얼럿창 및 입력 데이터 초기화가 구동되지 않고 브라우저가 홀딩됨. 그와 동시에 백엔드 서버 콘솔에는 비즈니스 검증 레이어가 깨지며 예외 로그가 연속으로 뿜어져 나옴.
```text
2026-06-03T01:17:29.037+09:00 ERROR 38280 --- [seoul-hub-backend] [nio-8080-exec-8] o.a.c.c.C.[.[.[/].[dispatcherServlet] : Servlet.service() for servlet threw exception [Request processing failed: java.lang.IllegalArgumentException: 이미 존재하는 이메일입니다.]

Hibernate: 
    insert into users (created_at, email, password, role) values (?, ?, ?, ?)
```

### 2. 원인 분석 (Root Cause)
- **API 계약 미스매치:** 백엔드 컨트롤러 단에서 가입 처리 성공 응답 시 객체가 아닌 순수 수치(`Long`) 형태의 날것만 던졌고, 중복 체크 시 원시 불리언(`Boolean`) 상태만 반환함. 반면 클라이언트 리액트 레이어는 구조화된 JSON 객체 구조인 `{ success, isDuplicated }` 명세를 파싱하도록 설계되어 조건문이 `undefined` 처리됨.
- **클라이언트 경합 조건 (Race Condition):** 성공 상태 시그널을 받지 못한 사용자가 화면 변화가 없자 가입 버튼을 고속 연타함. 첫 번째 패킷이 백엔드 내부로 유입되어 정상적으로 `INSERT` SQL 쿼리를 쓰기 지연 저장소에 올리고 실제 디스크 적재로 넘어가기 직전의 미세한 찰나(0.01초)에, 연이어 들어온 두 번째 패킷이 아직 트랜잭션이 커밋되지 않아 완전히 잠기지 않은 DB 상태를 읽어 `existsByEmail` 검증 선을 동시에 넘어옴. 이후 뒤늦게 처리되던 요청이 유니크 제약 및 비즈니스 예외선에 충돌하여 자폭을 터트린 데이터 스파이크 아키텍처 결함임.

### 3. 해결 방안 (Resolution)
- **백엔드 응답 표준화:** 자바 최신 스택 사양인 `record` 문법을 사용해 프론트엔드 통신 명세와 대칭을 이루는 전용 DTO 객체 쌍(`SignUpResponse`, `EmailCheckResponse`)으로 안전하게 직렬화 캡슐화를 완료함.
```java
public record SignUpResponse(boolean success, Long id) {}
```
- **프론트엔드 폼 상태 방어:** 가입 요청 시작과 동시에 자바스크립트 스레드 실행 및 HTML 엘리먼트 버튼 속성을 물리적으로 비활성화(Lock) 상태로 돌려놓는 `isSubmitting` 방어 코드 체인을 리액트 폼 전역에 설계 장착함.

### 4. 재발 방지 및 교훈 (Prevention & Lesson)
- 서버와 클라이언트 간의 데이터 통신 규약은 원시 타입의 원형 데이터를 직접 반환하면 역직렬화 예외 파싱 오류를 막기 어려우므로 반드시 표준화된 포맷 객체(Contract DTO)를 교환해야 함. 더불어 데이터의 생성 및 변형이 수반되는 모든 CUD 성격의 유저 입력 엔트리 포인트 단에는 레이스 컨디션을 방어할 프론트엔드 로딩 상태 락과 데이터베이스 유니크 키 제약조건의 이중 방어막을 의무화해야 함.

## 자카르타 검증 프로바이더 라이브러리 누락 및 도메인 엔티티 설계 결손 문제

### 1. 현상 (Issue)
- 회원 기능의 보안 강도를 강화하기 위해 비밀번호 복합 정규식 장치를 DTO에 심었으나, 규칙을 완전히 위반한 `test123` 같은 취약한 비밀번호가 검증 필터 없이 DB에 통과 적재됨. 이와 동시에 가입 양식에 기입한 사용자 이름(`name`) 자산은 흔적도 없이 사라지며 도메인 영속화 단계에서 데이터 정밀 위반 예외가 폭발함.
```text
org.springframework.dao.DataIntegrityViolationException: not-null property references a null or transient value for entity org.seoulhub.backend.domain.user.User.password
jakarta.validation.NoProviderFoundException: Unable to create a Configuration, because no Jakarta Validation provider could be found.
```

### 2. 원인 분석 (Root Cause)
- **자카르타 프로바이더 누락:** 자바 DTO 클래스 내부에 `@Valid` 지시어와 `@Pattern` 정규식 메타데이터 구문만 선언해 두었을 뿐, 정작 앱 런타임 환경에서 이 어노테이션의 유효성을 실시간 판별하고 프로세스를 통제할 구체적인 스펙 구현체 라이브러리(`Hibernate Validator`) 모듈이 `build.gradle` 명세서에 완전 누락되어 스프링 부트가 구문을 검사하지 못하고 그대로 스킵 처리함.
- **도메인 엔티티 모델 결손:** 프론트엔드에서 보낸 패킷 덩어리에는 이름(`name`) 자산이 정상 동봉되어 올라왔으나, 최종 종착지인 `User.java` JPA 엔티티 코어 소스코드 구조 내부에 `name` 멤버 변수 필드 및 빌더 바인딩 코드가 통째로 실종되어 있었음. 이로 인해 영속성 컨텍스트 조립 단계에서 이름 데이터가 강제 휘발 및 절단(Truncate)되는 모순이 겹쳐 발생함.

### 3. 해결 방안 (Resolution)
- 백엔드 빌드 시스템 스크립트(`build.gradle`)의 `dependencies` 그룹 내부에 유효성 검증 엔진 모듈을 긴급 추가 주입함.
```groovy
implementation 'org.springframework.boot:spring-boot-starter-validation'
```
- 이후 `User` 데이터베이스 엔티티 원형 내부에 `@Column(nullable = false) private String name;` 영속성 필드를 정식 개설하고, 변환 DTO 객체의 `toEntity()` 빌더 패턴 흐름에 누락된 이름 자산을 정방향 대칭 바인딩하여 테이블 구조 리모델링을 완수함.

### 4. 재발 방지 및 교훈 (Prevention & Lesson)
- 스프링 프레임워크 생태계 내에서 자카르타 및 부트 어노테이션 기반 검증 장치를 가동할 때는 이를 런타임 시점에 지원할 유효성 검증 프로바이더 엔진 라이브러리가 클래스패스에 필수적으로 안착해 있는지 패키지 명세서를 대조해야 함. 더불어 화면 UI 데이터 폼, 서버 전송 객체, 영속화 엔티티 구조는 데이터 누락 및 유실을 원천 방어하기 위해 완벽한 물리적 대칭성(Data Symmetry)을 유지하도록 아키텍처를 점검해야 함.
