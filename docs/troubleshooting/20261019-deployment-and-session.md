# 운영 전환과 계정·지도 문제 해결

2026-10-19까지의 작업 기록이다. 실제 발견한 오류와 요구사항 변경을 구분하고, 재현 조건·원인·해결·검증을 기록한다. 실제 비밀값이나 운영 회원 정보는 포함하지 않는다.

## 1. 화면 이동 후 대시보드 지도 미표시

- **현상:** 최초 진입이나 새로고침에서는 지도가 보이지만, 커뮤니티·계정관리에서 대시보드로 돌아오면 지도가 나타나지 않았다.
- **원인:** SDK 최초 다운로드의 `onLoad`에 초기화를 연결했다. 클라이언트 라우팅으로 컴포넌트가 다시 마운트될 때 이미 로드된 SDK에서는 동일 이벤트가 재발생하지 않았다.
- **해결:** Next.js Script의 `onReady`에서 `kakao.maps.load`와 지도 초기화를 수행하도록 변경했다.
- **검증:** 프런트 lint/build 후 사용자가 재배포한 운영 환경에서 커뮤니티·계정관리 왕복 시 지도 복원을 확인했다. 이후 캡처용 브라우저에서도 운영 지도 렌더링을 확인했다.
- **재발 방지:** 최초 진입뿐 아니라 다른 페이지로 이동한 뒤 재진입하는 경로도 확인한다.
- **근거:** 수정 커밋 `ac1589b`, [대시보드 코드](../../apps/frontend/src/app/dashboard/page.tsx).

## 2. 단일 세션 정책과 동시 로그인

- **상황:** 비밀번호 재설정은 기존 세션을 만료시켰지만 일반 로그인은 복수 세션을 허용했다. 이는 기존 정책이었으며, 운영 점검에서 최신 로그인 하나만 허용하도록 요구사항이 바뀌었다.
- **원인:** 성공한 로그인에서 새 세션을 생성하면서 기존 세션을 유지했다. 단순 삭제·생성만 추가하면 동시 로그인 요청이 겹칠 수 있다.
- **해결:** 사용자 행 잠금 트랜잭션 안에서 비밀번호·이메일 인증을 확인하고 기존 세션을 삭제·flush한 뒤 새 세션을 생성한다. 인증에 실패한 요청은 기존 세션을 삭제하지 않는다.
- **검증:** 동시 로그인 두 요청 후 유효 응답 200과 거부 응답 401이 하나씩 나오고, DB에는 해당 계정 세션이 하나만 남는 회귀 테스트를 추가했다. 실패한 로그인·다른 계정·이전 세션의 로그아웃이 최신 세션에 영향을 주지 않는지도 확인했다. 운영에서는 사용자가 일반 창과 시크릿 창에서 번갈아 로그인해 이전 창 차단을 확인했다.
- **제약:** 이전 창에 강제 이동을 푸시하는 방식은 아니다. 다음 인증 요청에서 거부하며 공개 대시보드는 계속 볼 수 있다.
- **근거:** 수정 커밋 `21af5dc`, [로그인 서비스](../../apps/backend/src/main/java/org/seoulhub/backend/domain/user/UserService.java), [단일 세션 테스트](../../apps/backend/src/test/java/org/seoulhub/backend/SingleSessionTests.java).

## 3. 실제 MySQL에서 스키마 검증 실패

- **현상:** 로컬 검증만으로는 드러나지 않았던 데이터베이스 식별자 대소문자 문제가 Docker의 MySQL 검증에서 발견됐다. 메타데이터 조회 대상이 `seoul_hub`에서 `SEOUL_HUB`로 바뀌어 테이블을 찾지 못했다.
- **원인:** MariaDB Connector/J와 Hibernate MySQLDialect 조합에서 식별자 대소문자 메타데이터의 기본 처리 차이가 있었다.
- **해결:** MySQL SQL 동작은 유지하면서 quoted/unquoted 식별자 처리의 fallback을 MIXED로 설정한 dialect를 사용한다. 운영 설정·배포 템플릿·마이그레이션 CI에 동일하게 반영했다.
- **검증:** MySQL 8.4의 빈 DB에서 Flyway V1~V4 적용, Hibernate validate, 컨테이너 health UP을 확인했다. 동일 DB로 재시작했을 때 마이그레이션을 중복 적용하지 않고 정상 시작하는 것도 확인했다. GitHub의 mysql-migration·container 작업으로 후속 검증한다.
- **교훈:** H2 MySQL 모드의 성공을 실제 MySQL 호환성 검증으로 간주하지 않는다.
- **근거:** [Dialect 구현](../../apps/backend/src/main/java/org/seoulhub/backend/global/config/MySqlMariaDbDriverDialect.java), [마이그레이션 테스트](../../apps/backend/src/test/java/org/seoulhub/backend/MigrationTests.java), [CI](../../.github/workflows/ci.yml).

## 4. 전체 거점 수집 지연과 최신값 보존

- **상황:** 호출 예산을 전체 거점 순환에 배분하면 사용자가 지금 보고 싶은 지역의 확인이 늦어졌다. 오래된 원시 관측을 삭제하는 방식도 최신 표시값과 이력 보존을 함께 다루기 어려웠다.
- **해결:** 검색·선택 거점을 최우선으로, 확대된 화면의 거점을 다음 순서로 처리한다. DB의 마지막 확인 시각을 기준으로 5분 캐시를 공유하고 하루 900회 앱 예산을 유지한다. 최신 관측·원시 이력·시간별 집계를 분리하고 이전 관측이 최신값을 덮어쓰지 않도록 한다.
- **검증:** 운영 지도에 실제 관측 인구와 관측 시각이 표시되는 것을 확인했다. 최신 관측은 이력 정리와 무관하게 유지하며, 같은 거점·시각의 중복 저장을 방지한다.
- **제약:** 900회는 앱 자체 예산이다. 화면 갱신을 원본 실시간 관측으로 표현하지 않는다. 원본 제공 지연과 서버 휴면은 별도로 표시하며 전체 지역의 연속 이력을 보장하지 않는다.
- **근거:** [수집·저장 정책](../population-data.md).

## 5. Windows Docker 엔진 시작 실패

- **현상:** Docker CLI는 설치됐지만 Server 정보를 받지 못했다. 처음에는 엔진 API 500, 이후에는 Linux 엔진 named pipe를 찾을 수 없다는 오류가 나타났다.
- **확인:** Docker Desktop은 Windows hypervisor가 실행되지 않는다고 표시했다. VirtualMachinePlatform은 Enabled였으나 부팅 설정의 `hypervisorlaunchtype`은 Off였다. WSL 설치나 기능 활성화만으로 하이퍼바이저 실행이 보장되지는 않았다.
- **대응:** 사용자 측 부팅 설정과 Windows 재시작·Docker 엔진 기동 확인 단계를 거쳤다. named pipe 오류만으로 애플리케이션 코드나 DB 설정을 변경하지 않았다.
- **검증:** 엔진 정상화 후 이미지 빌드, 임시 MySQL 마이그레이션, 컨테이너 health 검증을 완료했다. 임시 컨테이너·볼륨은 정리하고 기존 작업과 DB는 보존했다.
- **주의:** 이 기록은 시스템 설정 변경 명령을 일괄 실행하라는 안내가 아니다. 같은 오류라도 현재 하이퍼바이저 상태와 엔진 실행 상태를 먼저 확인한다.

## 검증 범위

백엔드 43개 테스트와 프런트 lint/build, 실제 MySQL 및 Docker 검증을 수행했다. 운영 메일 수신·계정 수명주기·단일 세션·지도 왕복은 사용자 확인을 포함한다. 포트폴리오 이미지 중 샘플 표시 화면은 UI 설명용이며 운영 인증·데이터 검증 증거로 사용하지 않는다. 부하 시험과 별도 DB 백업 복구 시험은 완료했다고 주장하지 않는다.
