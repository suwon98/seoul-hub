# 아키텍처 결정 로그 (Architecture Decision Log)

## 1. 리포지토리 구조 및 패키지 매니저
- **결정:** `pnpm Workspaces` 기반 모노레포(Monorepo) 구성
- **이유:** 단일 저장소 내에서 프론트/백엔드를 관리하여 실시간 소켓 통신 타입 공유 극대화. pnpm을 통해 무료 CI/CD 배포 플랫폼의 디스크 자원 및 빌드 시간 절약.

## 2. 개발 환경 분리 및 IDE 이원화
- **결정:** 백엔드는 IntelliJ (Java 21 + Spring Boot 4.0.6), 프론트엔드는 VS Code (Next.js 16) 채택
- **이유:** 각 영역의 실무 생산성을 극대화하기 위함. 단, 의존성 설치 및 전역 제어는 최상위 루트 터미널로 일원화하여 싱글 락파일(`pnpm-lock.yaml`) 유지.

## 3. 인프라 비용 0원 통제 및 무설치 개발 환경 (Cloud-First)
- **결정:** 로컬 PC에 MySQL/Redis를 설치하지 않고, 영구 무료 클라우드(Aiven MySQL, Upstash Serverless Redis) 연동
- **이유:** Windows 환경의 Redis 미지원 리스크 제거 및 로컬 환경 비대화 방지.
- **보충 프로덕션 노트:** 로컬 디버깅 생산성 및 데이터 주권 확보를 위해 로컬 환경에 한해 MariaDB 11.x 표준 포트 격리 인프라를 병행 가동하기로 변경 수립함.

## 4. API 명세서 문서화 자동화
- **결정:** Springdoc OpenAPI 사양 자동 추출 및 빌드 시점 내 순수 Node.js 스크립트를 통한 Notion 데이터베이스 동기화 구축.
- **이유:** 백엔드 코드 변경 사항이 문서에 실시간 반영되도록 하여 프론트엔드 개발자와의 소통 비용 및 사양 불일치 리스크를 격리함.

## 5. 실시간 인구 혼잡도 데이터 가상화 및 공용 타입 정의
- **결정:** 서울시 실시간 도시데이터에서 필요한 인구 상태 구조만 추출하여 `mocks/congestion.json` 파일로 규격화하고, 이를 `packages/types/congestion.ts` 인터페이스와 연동함.
- **이유:** 외부 공공 API 서버의 가동 상태와 무관하게 컴파일 및 비즈니스 로직 검증이 가능한 무중단 개발 환경을 구축하기 위함임. 또한 카멜케이스(camelCase) 정제 및 4단계 혼잡도 지표(GREEN, YELLOW, ORANGE, RED) 상수화를 통해 프론트엔드와 백엔드의 데이터 해석 규격을 일치시킴.

## 6. 백엔드 혼잡도 도메인 레이어 설계
- **결정:** 데이터베이스 영속화 엔티티(Congestion)와 네트워크 전송 객체(CongestionResponseDto)를 철저히 분리하고, 혼잡도 상태를 가리키는 문자열을 데이터 안정성을 위해 자바 자산 Enum(CongestionLevel) 구조로 강제화함.
- **이유:** 비즈니스 규칙 변경 시 엔티티 구조가 API 스펙을 직접 침범하는 현상을 방지하고, JPA 가동 시 문자열 하드코딩으로 인한 데이터 무결성 훼손을 방지하기 위함임.

## 7. 인구 혼잡도 조회 비즈니스 아키텍처 수립 (Slice-First)
- **결정:** 데이터베이스 영속 상태와 상관없이 클라이언트 요청에 무조건 대응하도록 레포지토리 결과 부재 시 가상 Mock 엔티티를 반환하는 방어적 서비스 레이어를 배포함. 또한 Springdoc 사양인 @Tag(name = "congestion")을 컨트롤러에 강제 적용함.
- **이유:** 외부 인프라 요인으로 데이터 적재가 지연되더라도 프론트엔드(Next.js) 레이어가 차단막 없이 API를 즉시 호출할 수 있는 병렬 개발 환경을 보장하기 위함임. 더불어 깃허브 액션즈 동기화 스크립트가 해당 태그를 읽어 노션 명세서에 자동으로 API 규격을 기록하도록 시스템 체인을 연동함.

## 8. 데이터베이스 모델링 수립 및 회원 코어 레이어 배치
- **결정:** 플랫폼 비즈니스를 관장할 4대 핵심 테이블(users, congestion_records, questions, answers)의 관계를 명문화한 ERD 자산을 `docs/database/erd.md` 경로에 배치함. 이와 동시에 이메일 기반 고유 식별 명세를 갖춘 회원 도메인(User, Role, UserRepository)을 기능 패키지 단위로 우선 안착시킴.
- **이유:** 게시판(Q&A) 및 웹소켓 알림 인프라 구축의 선행 조건인 유저 식별 관계를 완비하기 위함임. 외부 인프라 비용 청구 전에 관계형 데이터베이스 모델의 무결성을 컴파일 레이어에서 미리 검증하도록 구조를 고정함.

## 9. 회원가입 검증 객체 및 서비스 비즈니스 레이어 안착
- **결정:** 회원가입 요청 데이터의 형식 무결성을 컴파일 단계에서 1차 차단하기 위해 `UserSignUpRequestDto` 내부에 `@Email`, `@NotBlank` 검증 명세를 제약함. 아울러 중복 가입을 방어하는 `UserService.signUp` 비즈니스 레이어를 연결함.
- **이유:** 잘못된 규격의 데이터가 데이터베이스(users 테이블)까지 흘러 들어가 인프라를 오염시키는 것을 엔트리 포인트 초입에서 원천 차단하기 위함임.

## 10. 사용자 보안 정책 정교화 및 OAuth2 확장 청사진 수립
- **결정:** 회원가입 비밀번호에 8~16자 영문 대소문자/특수문자 필수 정규식(`@Pattern`)을 적용하고, 실시간 UX 대응을 위해 이메일 중복 확인 엔드포인트(`/api/v1/users/check-email`)를 서비스 초입에 배치함.
- **이유:** 클라이언트 엔드포인트 단에서 안전한 패스워드 생성을 강제하여 계정 보안 강도를 확보하기 위함임. 향후 도입할 Spring Security OAuth2 소셜 로그인 체인과의 유기적 통합을 위해 도메인 레이어 구조를 유연하게 개방 상태로 유지함.

## 11. API 응답 계약(API Contract) 표준화 및 Java 21 Record 도입
- **결정:** 백엔드 컨트롤러 계층의 모든 단일 API 응답 포맷을 원시 원형 타입 대신 불리언 상태와 고유 식별 주소(`id`)를 구조화한 전용 캡슐화 객체로 전격 선언함. 데이터 정제 효율화를 위해 자바 최신 문법 사양인 `record` 엔티티 구조를 채택함.
- **이유:** 클라이언트(프론트엔드 데이터 파서) 계층과 서버 컨텍스트 간의 JSON 직렬화 구조를 완벽하게 정렬하여, 원시 불리언이나 단일 숫자가 들어왔을 때 분기문이 작동하지 않는 UI 사이드 이펙트를 차단하고 API 가시성을 높이기 위함임.

## 12. 클라이언트 비동기 경합 조건(Race Condition) 물리 차단 정책
- **결정:** 모든 비동기 상태 제출 폼에 네트워크 통신 개시 시점부터 트랜잭션 최종 응답 시점까지 상태 스위치를 잠그는 `isSubmitting` 로딩 락 상태 레이어를 프론트엔드 전역 UI 폼에 의무 적용함.
- **이유:** 사용자의 의도치 않은 버튼 연타나 브라우저 이벤트 스파이크로 인해 동일한 데이터 패킷이 백엔드 데이터베이스 영속성 컨텍스트 계층에 0.01초 차이로 병렬 도달하여 분산 환경의 무결성을 깨뜨리는 현상을 엔트리 포인트 초입에서 완전히 방어하기 위함임.

## 13. 단방향 패스워드 해싱 메커니즘 및 BCryptPasswordEncoder 채택
- **결정:** 유저가 제출한 평문 패스워드를 데이터베이스 본진에 직접 노출하지 않고, 강력한 솔팅(Salting) 기반의 단방향 해시 알고리즘인 `BCryptPasswordEncoder` 빈(Bean)을 장착하여 영속화함.
- **이유:** 데이터베이스가 물리적으로 탈취당하거나 내부 조력자에 의한 침해가 발생하더라도 원본 패스워드의 역추적(복호화)을 복잡한 수학적 연산 구조로 원천 차단하여 사용자 계정 주권을 보호하기 위함임.

## 14. 토큰 기반 무상태(Stateless) 아키텍처 및 JWT(Json Web Token) 도입
- **결정:** 서버의 세션 메모리 영역을 사용하는 전형적인 상태 유지 방식 대신, 인가 정보가 담긴 1시간 수명의 임시 통행증인 JWT(Access Token)를 JJWT 0.12.x 최신 표준 사양으로 발행하도록 아키텍처를 고정함.
- **이유:** 서버 메모리에 유저의 로그인 상태를 얹지 않으므로 세션 클러스터링 오버헤드를 완벽히 제거할 수 있으며, 향후 시스템 스케일아웃(확장) 및 모바일 앱 레이어, 오픈 API 확장 청사진과의 유기적 연동을 유연하게 개방해 두기 위함임.

## 15. 보안 컨텍스트 필터 체인(PermitAll) 범위 한정 구성
- **결정:** 스프링 시큐리티가 애플리케이션 전역을 통제하되, 회원가입(`/signup`), 이메일 중복 체크(`/check-email`), 로그인(`/login`) 및 오픈 API 명세서 추출 경로(`/swagger-ui/**`, `/v3/api-docs/**`)에 한해서는 시큐리티 검문을 면제(`permitAll`)하도록 화이트리스트 필터를 분리함.
- **이유:** 핵심 정문 보안 아키텍처는 견고하게 잠그되, 유저가 진입하기 전 단계의 필수 퍼블릭 엔드포인트와 자동화 문서화 인프라의 가용성을 완벽하게 보장하여 프론트엔드와 백엔드의 병렬 개발 생산성을 훼손하지 않기 위함임.

## 16. OncePerRequestFilter 기반의 커텀 JWT 인증 필터 배치
- **결정:** 모든 인가 요구 API 요청의 초입에서 `Authorization` HTTP 헤더를 파싱하여 Bearer 토큰의 무결성을 검증하고 시큐리티 컨텍스트에 인증 도장을 찍어주는 `JwtAuthenticationFilter`를 커스텀 구현하여 `UsernamePasswordAuthenticationFilter` 전단에 결합함.
- **이유:** 서블릿 필터 레이어 최전방에서 유효하지 않은 토큰이나 만료된 요청을 1차적으로 차단하고, 통과된 정당한 요청에 한해서만 도메인 컨트롤러(JPA 영속성 컨텍스트 계층)로 제어권을 안전하게 위임하기 위함임.

## 17. OpenAPI(Swagger) 글로벌 보안 스키마(Security Scheme) 강제 주입
- **결정:** 백엔드 시큐리티 성벽과 대칭을 이루도록 `OpenApiConfig` 설정을 개설하고, 스웨거 전역 대시보드에 HTTP Bearer JWT 규격의 `SecurityScheme`을 주입하여 우측 상단에 `Authorize` 자물쇠 팝업 엔진을 활성화함.
- **이유:** 개발자 및 프론트엔드 협업자가 로컬 환경이나 외부 포스트맨(Postman) 같은 별도 도구 없이도, 오직 스웨거 웹 대시보드 내부에서 원스톱으로 JWT 토큰 인증 스냅샷을 들고 인가 제한 API(`GET /api/v1/congestion`)를 유연하게 테스트 및 검증할 수 있도록 가용성을 극대화하기 위함임.

## 18. 프론트엔드 비동기 데이터 통신 계층의 대칭 인터페이스 단일화
- **결정:** 백엔드의 영속화 엔티티 및 직렬화 JSON 포맷 변경에 유기적으로 대응할 수 있도록, 기존 프론트엔드 내 중복되거나 파편화되어 있던 `CongestionResponse` 인터페이스 명세를 완전히 폐기하고 실제 제공 스펙 사양 하나로 통합 일원화함.
- **이유:** 클라이언트와 서버 레이어 간의 데이터 타입 미스매치(Type Mismatch)로 인한 런타임 역직렬화 에러를 컴파일 단계에서 철저히 차단하고 데이터 구조의 무결성을 격리하기 위함임.

## 19. 클라이언트 환경 변수 기반 엔드포인트 일원화 및 라우팅 가드 수립
- **결정:** 모든 외부 비동기 네트워킹 코드가 `NEXT_PUBLIC_API_URL` 환경 변수를 정방향 경유하도록 구조를 제어하고, 대시보드 페이지 진입 초입에 브라우저 로컬 스토리지 내 JWT 토큰 존재 유무를 판별하여 비인증 유저를 로그인 폼으로 강제 축출하는 라우팅 가드(Routing Guard)를 설계함.
- **이유:** 개발, 스테이징, 상용 프로덕션 인프라 환경 변화에 코드 수정 없이 대응할 수 있는 확장성을 확보하고, 악의적인 다이렉트 URL 주소 진입을 엔트리 포인트 최상단에서 원천 차단하기 위함임.

## 20. 다대일(ManyToOne) 단방향 연관 관계 및 지연 로딩(LAZY) 채택
- **결정:** `Question`(질문) 엔티티가 `User`(회원) 엔티티를 참조할 때, JPA 표준 사양인 `@ManyToOne` 단방향 연관 관계를 수립하되 글로벌 페치 전략을 `FetchType.LAZY`(지연 로딩)로 강제 차단함.
- **이유:** 질문글 엔티티를 조회할 때 무분별하게 작성자 회원 테이블까지 즉시 조인(EAGER)하여 가져오는 N+1 쿼리 오버헤드를 원천 차단하고, 실제 화면단이나 로직에서 유저 객체를 물리적으로 호출하는 시점에만 프록시를 통해 쿼리가 쏘아지도록 메모리 및 네트워크 성능을 최적화하기 위함임.

## 21. Principal 컨텍스트 객체를 통한 인가 식별자 동적 바인딩
- **결정:** `QuestionController` 계층의 등록 엔드포인트 파라미터로 `java.security.Principal` 구조를 선언하여, 서블릿 필터가 시큐리티 컨텍스트에 임포트해 둔 인증 유저의 고유 식별자(이메일)를 스프링 아규먼트 리졸버를 통해 다이렉트로 공수하도록 설계함.
- **이유:** 프론트엔드가 페이로드 바디에 작성자의 식별자를 하드코딩해서 던지는 위조 취약점을 원천 폐쇄하고, 오직 변조 불가능한 인증 토큰(JWT) 컨텍스트 내부의 정보만을 신뢰하여 영속성 외래키 매핑의 보안 무결성을 완벽하게 격리하기 위함임.

## 22. 시큐리티 필터 체인 기반 CORS(Cross-Origin Resource Sharing) 제어 수립
- **결정:** 프론트엔드 오리진(`http://localhost:3000`)의 교차 출처 비동기 요청 및 `Authorization` 커스텀 헤더가 포함된 OPTIONS 사전 정찰 패킷(Preflight)을 공식 수용하도록 `SecurityConfig` 필터 체인 최전단에 `CorsConfigurationSource` 표준 명세를 바인딩함.
- **이유:** 웹 브라우저 고유의 동일 출처 정책(SOP) 보안 사양을 충족하면서도, 모노레포 아키텍처 환경 내에서 백엔드와 프론트엔드 간의 토큰 기반 API 수송 회선을 안전하고 유연하게 동기화하기 위함임.

## 23. 이중 다대일(ManyToOne) 단방향 연관 관계 및 완전 지연 로딩 수립
- **결정:** `Answer`(답변) 엔티티가 `Question`(질문)과 `User`(회원) 엔티티를 동시에 참조하도록 구조를 짜되, 양쪽 모두 `@ManyToOne(fetch = FetchType.LAZY)` 페치 전략을 강제 적용함.
- **이유:** 하나의 답변 자원을 호출할 때 대상 질문 본문과 회원 프로필이 무분별하게 조인(EAGER)되어 발생하는 데이터베이스 네트워크 과부하 및 N+1 성능 병목 현상을 원천 방어하기 위함임.

## 24. RESTful 규례에 따른 종속 계층형 URI 경로 구조 채택
- **결정:** 답변 자원의 엔드포인트를 독립적인 독립 경로로 개설하지 않고, 명확한 소유 관계를 나타내는 상위 질문 자원 하위의 계층형 구조인 `/api/v1/questions/{questionId}/answers` 포맷으로 설계함.
- **이유:** 외부 API 소비자가 URI 명세만 보고도 "특정 질문에 종속된 댓글/답변 자원"임을 직관적으로 식별할 수 있도록 자원의 식별성과 관계성을 REST 아키텍처 스타일에 맞춰 고정하기 위함임.

## 25. Next.js 동적 라우팅(Dynamic Routes) 및 병렬 데이터 페칭 채택
- **결정:** Q&A 상세 도메인 진입을 위해 `app/questions/[id]` 계층의 동적 라우팅 방식을 채택하고, 상세 본문 및 댓글 목록을 불러올 때 `Promise.all` 구조를 통해 병렬 비동기 통신을 수행함.
- **이유:** URL 경로 스냅샷에서 고유 식별자(ID)를 동적으로 추출하여 화면을 격리하고, 단건 조회 API와 종속 댓글 조회 API를 동시 병렬 피딩함으로써 클라이언트 네트워킹 레이턴시를 최소화하고 화면 렌더링 속도를 최적화하기 위함임.

## 26. 데이터 보존 정책(Data Retention Policy) 기반 오토 클리닝 스케줄러 배치 도입
- **결정:** 혼잡도 데이터 레코드가 무한히 인서트되는 인프라 과부하 리스크를 제어하기 위해, `@Scheduled(fixedDelay = 60000)` 규격의 1분 주기 백그라운드 배치를 개설하고 현재 시점 기준 5분이 경과한 과거 만료 데이터를 `@Modifying` 벌크 쿼리로 일괄 자동 삭제하도록 구조화함.
- **이유:** 지속적인 데이터 유입 환경 속에서 MariaDB 스토리지 디스크 용량 고갈 및 인덱스 비대화로 인한 데이터베이스 성능 저하를 예방하고, 실시간성 트래픽 모니터링에 필요한 유효 데이터 최신 스냅샷 수량(약 150건 내외)만을 효율적으로 유지관리하기 위함임.
