# 공식 거점과 관측 저장 구조

2026-10-18 로컬 구현. 외부 배포는 실행하지 않았다.

## 공식 카탈로그

출처: https://data.seoul.go.kr/dataList/OA-21778/A/1/datasetView.do
공식 첨부 서울시 주요 121장소 목록.xlsx(seq=15)와 영역.zip(seq=16)을 코드·명칭으로 대조했다.
카탈로그: apps/backend/src/main/resources/seoul-areas.json. 출처와 원본 SHA-256은 seoul-areas-source.json.
지도 대표 좌표는 공식 WGS84 영역의 bounding-box 중심이다. 실제 경계나 서울 전체의 연속적인 인구 분포를 표현하지 않는다.
기존 홍대입구역/명동/이태원 별칭도 수용하며 서울시에는 공식 POI 코드를 전송한다.

## 저장·조회

- congestion_latest: 공식 장소 코드당 최신 관측 1건. 오래된 이력 삭제와 무관하게 유지한다.
- congestion_records: 장소명+관측 시각 고유 제약. 원본 관측 이력 48시간 보관.
- congestion_hourly_stats: 시간별 평균 30일 보관. 최근 24개 완료 시간을 5분마다 재계산해 지연 관측을 반영한다.
- update_time은 서울시 관측 시각, collected_at은 서버가 최초 저장한 시각이다. 과거 데이터의 알 수 없는 수집 시각은 NULL이다.
- 이전 관측이 늦게 도착하면 이력에는 저장하지만 최신 값은 덮어쓰지 않는다. 같은 관측 시각은 중복 저장하지 않는다.
- 목록·상세 GET은 저장 데이터만 읽으며 서울시 API를 호출하지 않는다. 화면 갱신은 30초이며 원본 수집 주기와 다르다.
- 혼잡도 등급은 관측 당시 값을 유지한다. 관측 나이 45분 이상은 DELAYED(점선), 120분 이상은 EXPIRED(흐림), 관측 없음은 UNAVAILABLE로 별도 표시한다. 이는 앱의 표시 정책이며 서울시 SLA가 아니다.
- 정리는 매시간 수행한다. API 장애나 장기 휴면에도 마지막 관측은 남는다.

## 화면·선택 기반 수집 (현재)

- 검색·선택 거점이 최우선, 확대된 지도 안의 거점이 다음 순서다. 화면에서는 중심에 가까운 최대 12곳을 요청한다. 서버는 요청당 최대 20개 공식 거점만 수용한다.
- 지도 이동 정지 후 500ms 지연하여 관심 영역을 교체한다. 클라이언트별 증가 순번으로 늦게 도착한 이전 화면 요청을 무시한다.
- 지도 레벨 8 이상(서울 전체 보기 포함)은 선택 거점만 갱신한다. 전체 현황은 저장된 관측을 표시한다. 사용자가 없는 지역은 자동 수집하지 않는다.
- 브라우저는 15초마다 관심 영역을 유지하며 비활성 탭은 비운다. 연결이 끊긴 관심 영역은 45초 후 만료한다. 프로세스 재시작 시 관심 영역은 다시 등록된다.
- 서버 단일 작업자가 선택 거점을 먼저, 같은 우선순위에서는 마지막 API 확인이 가장 오래된 거점을 먼저 처리한다. 이미 진행 중인 원본 호출은 취소하지 않는다.
- 공통 캐시는 DB의 last_checked_at 기준 5분이다. 원본 관측이 오래되어도 최근에 확인했다면 재호출하지 않는다. 여러 브라우저가 같은 거점을 요청해도 작업자는 캐시를 재확인하여 요청을 합친다.
- 통신 실패 시 마지막 관측을 보존하고 같은 거점은 최소 60초 후 재시도한다. 실패도 일일 예산에 포함한다.
- 조회 GET은 원본 호출을 하지 않는다. POST /api/v1/congestion/refresh는 관심 영역만 등록한다. UI는 저장값을 먼저 표시하고 5초마다 DB 결과를 다시 읽는다. 검색 즉시 원본 응답 완료나 실시간 현장 인구를 보장하지 않는다.
- 관측 시각, 최초 수집 시각, 마지막 API 확인 시각은 계속 구분한다. 원본 제공 지연은 수집 우선순위로 해소할 수 없다.

설정:
```
SEOUL_COLLECTION_DAILY_BUDGET=900
SEOUL_COLLECTION_REQUEST_DELAY_MS=1000
```
일일 예산과 속도 제한을 분리했다. 원본 호출 사이 최소 1초(설정이 더 크면 그 값)이며, 요청 8초 제한의 직렬 작업이다. 이전 TARGET_CYCLE 설정과 96초 균등 배분은 더 이상 사용하지 않는다.
seoul_api_budget의 한국 날짜별 카운터와 다음 허용 시각은 DB에 유지한다. 기존 카운터를 초기화하지 않는다. 예산 소진 시 다음 한국 날짜까지 저장된 관측을 표시한다. 여러 프로세스 배포는 별도 분산 작업자 설계가 필요하며 현재는 단일 백엔드 기준이다.

하루 900회는 사용자가 유지하기로 한 앱 자체 제한이다. 사용자가 확인한 이용안내는 일반 API의 호출 횟수 제한이 없고 실시간 지하철만 일일 1,000회로 구분한다. 공개 자료: https://data.seoul.go.kr/together/guide/useGuide.do
이 앱 밖에서 동일 키를 사용한 호출과 카운터 도입 전 호출은 포함하지 않는다.
인구 API는 한 장소씩 호출한다: https://data.seoul.go.kr/dataList/OA-21778/A/1/datasetView.do
원본 갱신 주기 5분: https://data.seoul.go.kr/dataVisual/seoul/guide.do
Render 서버 휴면 시 수집은 중단되며 이력은 관심이 있었던 지역·시간에 한해서만 쌓인다. 전체 지역의 연속 시계열을 보장하지 않는다.

## 마이그레이션 및 복구

운영 Flyway V3는 collected_at 및 congestion_latest를 추가한다. V4는 last_checked_at과 seoul_api_budget을 추가한다. 시작 시 기존 이력의 관측 시각 기준 최신값을 별도 테이블로 보완한다.
local은 기존 H2 파일에 Hibernate update를 적용하고 동일한 보완 절차를 수행한다. 사용자 계정·게시물은 변경하지 않는다.
로컬 변경 전 백업: apps/backend/data/seoul-hub.before-area-expansion.mv.db (Git 제외, 개인정보 포함).
백업 복구는 백엔드를 종료한 상태에서만 수행한다. 백업 파일은 외부 공유하지 않는다.
